# Testing Guide

> **Owns:** test-quality rules for every suite in the repo, the test pyramid and its environments (which DB engine and crypto provider runs where), the **chaos harness** normative spec (v0 exit criterion D4.1: fixtures, determinism, the convergence oracle, the scenario catalog with pass criteria), and the on-device performance gates. Envelope/hashing/rejection semantics live in `05-operation-log.md`; the sync wire protocol in `api/01-sync.md`; the module contract and projection-engine rules in `04-module-contract.md`; state-machine states in `03-state-machines.md`; PIN lockout machine (schedule, states, recovery) in `api/02-auth.md` §6.5; media chunk protocol in `api/03-media.md`; label-catalog mechanism in `07-i18n.md`.
> **Change control:** change this doc first, then the code. A test that contradicts this doc is wrong even if it is green.

## 1. Part A — Test-quality rules (apply to every suite)

| # | Rule |
| - | ---- |
| **T-1** | **Test public behavior only.** The public surfaces are: command execution (`execute(command, input, ctx)` → ops/result/`DomainError`), queries (input → `{rows, nextCursor}`), the sync wire protocol (requests/responses/rejection codes per `api/01-sync` and `05 §8`), state-machine transitions on bookkeeping (`syncStatus`, `uploadStatus`, per `03-state-machines`), and label **keys**/testIDs/accessibility roles in the UI. Tests must never: import an applier directly (appliers are exercised only through the projection engine and the applier conformance suite §2.4), spy on internal functions, assert call counts of internals, or read projection tables except through queries or the harness oracle (§3.4). |
| **T-2** | **One behavior per test.** Each test asserts exactly one behavior and its name states it (`rejects push with CHAIN_BROKEN when previousHash mismatches`). A test needing "and" in its name is two tests. |
| **T-3** | **Unique values per case.** No shared magic constants (`TEST_TENANT_ID`, `NOTE_1`) reused across test cases — shared constants make tests pass by coincidence and fail in bulk. Every case builds its own values from a seeded fixture factory (`makeFixture(seed)`, §3.3); two tests shall never assert on the same literal id, title, or timestamp. |
| **T-4** | **Never assert UI copy.** Labels change via the label catalog (`07-i18n`) without touching tests. Assert label **keys**, `testID`s, and accessibility roles — never rendered strings. The i18n lint rule (no hardcoded user-facing strings) is owned by `07-i18n`; tests asserting copy are a violation of that rule by proxy. |
| **T-5** | **No snapshot tests of component trees.** `toMatchSnapshot()` on rendered trees is forbidden — it asserts everything, therefore nothing. The ONLY permitted golden files are **wire-format vectors**: JCS canonical bytes, SHA-256/Ed25519 test vectors, envelope JSON fixtures. These are hand-reviewed spec artifacts, updated only via a change to the owning spec doc. |
| **T-6** | **Determinism.** No test reads the real clock, real RNG, real network, or real timers. `04 §5.2` deliberately gives handlers **no clock** — the runtime stamps `timestamp`; therefore the runtime (client and server) shall accept an injected `Clock` at construction (`{ now(): number }`), production default = system clock, tests = `FakeClock` (§3.3). Ids: `ctx.newId()` delegates to an injected `IdSource`; the test `IdSource` builds valid UUIDv7 from `FakeClock` ms + seeded-PRNG random bits, so ids (and canonical ordering) are stable per seed. Retry/backoff logic runs on fake timers. A test that sleeps is a bug. Every randomized test prints its seed on failure and is reproducible from that seed alone. |
| **T-7** | **Production code under test.** Fakes exist only at I/O boundaries: `fetch`, clock, RNG/id source, filesystem, keystore, camera. Never mock or reimplement `@bolusi/core` logic (canonicalization, hashing, chaining, sync loop, projection engine) inside a test — the harness in particular drives the real sync engine against the real server handler (§3.1). |
| **T-8** | **Both-engine rule for appliers.** `04 §2` requires appliers to be dialect-neutral. Every module's appliers run through the shared applier conformance suite against BOTH engines (SQLite via the shim, Postgres via PGlite — §2.4) with oracle-equal output (§3.4). A module without this suite passing does not merge. **Scope — what this gate does NOT prove (T-14f; state it, because a gate implying absent coverage is worse than no gate):** (a) **driver marshalling.** Both legs run clients that return `int8` as a **number**; the production client (`pg`) returns it as a **string**. **And the gap is narrower than "PGlite misses everything" — it is worse: PGlite misses exactly the bug that fails silently.** Measured (task 48, three bugs in one decoder, each reverted in isolation on both lanes): jsonb → **9 RED on both**; boolean → **1 RED on both**; int8 → **PGlite 14/14 GREEN, real `pg` 4 RED**. PGlite catches the classes that *throw* and is blind to the one that returns a plausible wrong answer. So a PGlite-green falsification of an int8 fix is the bug's **alibi**: you see 14/14 and conclude the fix isn't load-bearing. "Postgres" here means *PGlite*, over a driver production never uses — so a bigint `===`/arithmetic bug is green on both legs and broken in production (task 46). Only an attributed real-PG16 lane covers that: `pnpm test:rls`, e.g. `packages/db-server/test/projection-int8-marshalling.test.ts`. **THIS LEG STAYS PGlite UNDER D16, AND THAT IS A RULING, NOT AN OVERSIGHT (task 73).** D16 moves L3 to real PG16 in a container, but **this gate structurally cannot follow**, and the reason is worth stating so nobody re-opens it: the runner lives in `packages/core/test/`, and `core` may import neither `pg` (§3.3 rule 3, platform-free) nor `db-server` — the latter because **`db-server` imports `core`, so the edge `core → db-server` is a dependency CYCLE**, not a policy question. Moving this leg therefore requires either a §3.3 change putting `pg` in core's test graph, or relocating the runner out of `core` entirely. Neither is justified, because **D16 rule 3 is satisfied exactly as written**: this gate's question is *dialect* neutrality, PGlite answers it honestly, real PG16 also answers it, and — critically — **this gate is no longer the sole witness for anything**. The marshalling claim it cannot make is now made by a lane that runs the production driver (`pnpm test:rls`, real PG16 via testcontainers). A substitute is legitimate *because* something else is the witness; that is the whole of rule 3. (b) **the pull path.** The suite drives `applyAppendedOp` only, which takes the engine's `advanceLocalSeq` branch — `highestContiguousServerSeq` and the serverSeq watermark are never executed by this gate on either engine. Extending the gate to a bigint-bearing read does not make it cover (a); a new claim about marshalling needs the real driver, not a third dialect. **(c) SEMANTICS. The oracle compares the two engines to EACH OTHER, so it is blind to anything both engines get identically wrong** — which is every applier bug that isn't dialect-specific. Proven by falsification (task 17, confirmed by review-17): removing `03 §7`'s `status='surfaced'` predicate left the **digest test GREEN** — both engines folded the same wrong answer, so their digests matched — and only the *semantics* test went red (`expected 'op-0004' to be 'op-0003'`). So T-8's green means *"the two engines agree"*, **not** *"the applier is correct"*. A module needs assertions about what the projection should CONTAIN, separate from the cross-engine digest; the conformance suite is a **dialect** gate wearing a correctness gate's name. This is the T-14 family again — interrogate the oracle: ask what question it actually answers, which here is a comparison, not a claim. |
| **T-9** | **Security surfaces ship adversarial tests before review** (CLAUDE.md §2.5). The harness scenarios CHAOS-05 (tamper), CHAOS-10 (gzip), CHAOS-11 (PIN), CHAOS-12 (pull injection) are the floor, not the ceiling — new security surface = new adversarial cases in the same style. |
| **T-10** | **A flaky test is a P1 bug.** No quarantine directory, no auto-retry-until-green. Fix the nondeterminism or delete the test with a written cause in the commit subject. |
| **T-11** | **A guard is only load-bearing if someone has watched it go red.** Every gate, guard, sweep, probe, and adversarial test SHALL be **falsified before it is believed**: break the thing it protects, observe the specific failure, restore, observe green. State the falsification in the PR/report — "I broke X, saw Y fail, reverted" — not "the test passes". An inoperable gate and a passing gate are the same colour, so the only way to know a gate runs is to make it go red on demand; and a fix is not exempt from the rule it enforces (two of the fake greens were introduced *by the fix for another fake green*). When you add a skip/park/placeholder path, ask immediately: does the checker still see what I just set aside? The roster of eight-plus gates green for the wrong reason, with each mechanism and falsification, is in [`incidents.md`](incidents.md) INC-T11. |
| **T-12** | **Test the class, not the instances you thought of.** When a bug is found, ask what *class* it belongs to and enumerate that class programmatically — a suite built from remembered examples can only catch remembered examples. Worked example (base64 padding position vs padding bits, 16 variants): [`incidents.md`](incidents.md) INC-T12. |
| **T-13** | **Interrogate the oracle.** A test is only as good as its reference for "correct". Before trusting a comparison, ask what decides truth in it, and whether that thing is stricter than the code under test. Golden vectors are extracted programmatically from their source spec, never hand-transcribed. Why (Node's `Buffer.from` accepts malformed base64; a hand-typed vector already wrong `25` vs `5c`): [`incidents.md`](incidents.md) INC-T13. |
| **T-14b** | **An empty result and a correct result look identical — assert the fixture before believing the absence.** Any test whose pass condition is *nothing came back* (`0 rows`, `UPDATE 0`, no findings, empty diff) SHALL first assert the thing it expects to be filtered out actually **exists**. A local `pnpm test:rls` green means nothing without it (CI is unaffected — isolated service container). This is T-14 in the data plane. Incident (shared docker daemon reset the schema mid-probe → vacuous RLS green): [`incidents.md`](incidents.md) INC-T14B. |
| **T-14c** | **A stale build is a fake green — test the code you think you're testing.** When one lane imports a package's **built** artifact (`dist/`) and another imports **source** (`src/`), a run without a preceding `tsc -b` tests stale code and passes against yesterday's bug. Guard it: make `test` depend on `build`, make both lanes import the same entry, or assert build-freshness (dist mtime ≥ src mtime). CI that runs `tsc -b` before the test stage is protected; a bare local `pnpm test` is not. Incident (`@bolusi/core` jcs-guards `dist/` vs the Hermes vector runner `src/`): [`incidents.md`](incidents.md) INC-T14C. |
| **T-14d** | **Know which database answered — an unattributable green is not a green.** Believe a DB number only if its run printed the `attribution OK` provenance line; never re-pin the dev compose `ports:` to a fixed `5432` (the host port is ephemeral and per-worktree, `DATABASE_URL` derived from `docker compose port` by `scripts/db-lane.mjs`, a failed `db:up` fatal to the lane, each cluster stamped `bolusi.db_owner` and verified by `packages/db-server/test/global-setup.ts` before any test runs); never `docker compose down` a container that is not yours (`pnpm db:down` removes only your own). Two worktrees on one database corrupt each other's fixtures, surfacing as flakiness (T-10), not misconfiguration. Incident (a `test:rls` "82/11 on real PG16" served by another worktree's leaked container; closed by task 34 by construction): [`incidents.md`](incidents.md) INC-T14D. |
| **T-14e** | **A number measured in a worktree is a number *about that worktree* — evidence has a scope and a timestamp, and quoting it elsewhere strips both.** This scales with parallelism: the more agents in flight, the more likely main has moved under any branch's evidence. (1) a number that lands in a **durable doc** (spec, §7 record, acceptance criterion) is **re-measured against the merged result**, not copied from the branch; (2) if you cannot re-measure, cite the scope ("22/162 *as of merge-base `abc123`*"); (3) reviewers check quoted numbers against main, not the branch that quoted them. Incident (task 32's "22/162" stale in a spec by merge time): [`incidents.md`](incidents.md) INC-T14E. |
| **T-14f** | **"Both engines" is not "both drivers" — the client decides the JS type, and PGlite is not `pg`.** The production `pg` driver returns `int8`/`bigint` as a **string**; better-sqlite3 and PGlite return a **number**, so a bigint `===`/arithmetic bug is green on every test lane and broken in production. Probe a **digit-count boundary** (9→10, 99→100), never a big number: the bug is lexicographic string ordering, so a value near 2^53 is *correct by luck* and becomes the bug's alibi. (1) a claim about *driver marshalling* is only proven by a lane running the **production driver** — for Postgres that is `test:rls`'s attributed real PG16, never PGlite; (2) never let a raw `sql<{…: number}>` stand over an int8 column without a cast a test can demonstrate — write explicit aliases (`byte_size AS "byteSize"`), because `CamelCasePlugin` (production, `db-client/src/connection.ts:185`) rewrites raw result keys too and `Number(undefined)` is `NaN` on the wire; a hand-written type argument is a claim `tsc` accepts without evidence (family: task 39 `DB`-is-`any`, task 46 int8, task 18 keys); (3) when a gate's name says "Postgres", write down **which** Postgres and **over which client** — D16/task 73 fixes L3 as `postgres:16` in a testcontainer over real `pg` 8.22.0 as `bolusi_app` (NOBYPASSRLS); a gate running a substitute names it and names the lane carrying the claim it cannot make, and never uses `.withReuse()` (a provenance defect — T-14d wearing testcontainers). Finding the mechanism is not finding the class (T-12). Incidents (the 2^53 alibi verified in Node, the watermark that never advanced, the `NaN`-on-the-wire): [`incidents.md`](incidents.md) INC-T14F. |
| **T-14g** | **A test can go inert *because the fix landed* — when you change the shape a test was written against, re-ask what it now proves.** A test can catch a real flaw, the fix removes the code path it reached through, and the green now asserts nothing. (1) when a fix changes the *shape* a test targets, re-derive what the test now executes; (2) a test whose fixture can be **deleted with no effect** is inert — prove a load-bearing setup by deleting it and watching red; (3) make the oracle as narrow as the claim (`/exceeds/` distinguishes the two throws, `/server_seq/` cannot). Incident (task 46's 2^53 test passed with its seeded row deleted): [`incidents.md`](incidents.md) INC-T14G. |
| **T-14h** | **A loud failure upstream of silent ones is not "the first bug to fix" — it is the only witness they have.** When several bugs sit on one path and one *throws*, no assertion downstream of it executes; fixing the loud one alone **deletes the evidence** for the silent ones and the suite gets *quieter*. (1) when a path throws, assume it is **masking** — revert-in-isolation to measure each bug's own signal; (2) **count failure modes, not failures** (`10 SyntaxError, 0 AssertionError` is the tell your oracles never ran); (3) a partial fix on a multi-bug path is worse than none — the remaining bugs are now unwitnessed *and* the tree looks better. Incident (`RawOpRow`'s three bugs: 9 failed / 110 passed, 0 AssertionError): [`incidents.md`](incidents.md) INC-T14H. |
| **T-15** | **Ask "if this were wrong, what would notice?" — and when the answer is "nothing", that is the finding.** It catches the two siblings no test, type, lint, or exit code sees: **a call that changes nothing** and **a test that checks something real that nothing calls** — both green. The common cause is that **the comment was the guard**: an accurate, spec-citing comment supplies the reader's confidence so they stop checking. So comments are not evidence — a claim a comment makes about a mechanism is a **hypothesis to falsify**, at the platform docs and by breaking the thing; **"typed and compiling" is not "running on the target"** (verify the option's *platform column*, not just that the symbol exists). And when a claim holds on platform A and is unverified on platform B, A's success is not evidence — it is the mechanism concealing B's failure; ask which platform is carrying the claim, and whether it carries it *for* the other. Incidents (iOS-only `keychainAccessible`; the channel write Android ignores; `canAttempt`'s 11 tests/0 callers; unregistered `expo-location`; a prospective catch; a self-correction that was itself an INC-T16): [`incidents.md`](incidents.md) INC-T15. |
| **T-16** | **A mention is not a producer, and it lies in BOTH directions.** `grep` answers *"is this string here?"*, never *"does this behaviour exist?"*, and the two are uncorrelated **both ways** — a false comment makes dead code look alive; an absent title makes live behaviour look dead. **(1)** before declaring something **unshipped**, trace to a **producer** — the code that would do it and the test that would fail; "no one titled it" is not evidence. **(1b)** the recurring shape is **the ring** — a cycle of mentions where every file names another and nobody builds it, each pointer reading as diligence; it survives any amount of reading, so **the instrument that breaks it is the compiler/language service** (`TS2741`), not reading — ask the tool to PRODUCE the thing (clause 5). **(2)** before declaring something **live**, trace to a **caller** — a comment, docstring, label key, or enum value in a round-trip test are all mentions. **(3)** for "is this called?", text search is the wrong instrument — use the language service (`ts-morph findReferences`, `knip`) and prove it on a known case first. **(4)** any sweep reporting a denominator states what it **cannot** see; **(4b)** an instrument's false-negative outweighs its false-positive and only the latter is ever noticed — **before believing a green sweep, make it go red on a known case**. **(5)** existence questions are answered by **PRODUCING the thing** (resolve the config, ask the language service, run the migration, read the generated manifest); if your evidence is a text search you have not answered the question. **(6)** the same trap catches **performance explanations** — if you catch yourself EXPLAINING a timing number, run the experiment instead. Incidents (the decoy sweep missing `canAttempt`; task 31/54's refuted premise; the three rings incl. the SQLCipher key; the cries-wolf mention-counter; the `fileParallelism` false cause): [`incidents.md`](incidents.md) INC-T16. |
| **T-17** | **A fence test needs a positive control, or it proves only that nothing happened.** An isolation assertion — *"tenant A cannot read tenant B's row"*, *"the revoked device's ops are not accepted"*, *"no plaintext token is in the DB"* — is satisfied **trivially** when the fenced thing never existed: `expect(rowsVisibleToA).toBe(0)` also passes when B's write silently failed or the seed missed. The green means "absent", and a broken setup produces "absent" too. So every fence ships two assertions: the **fence** (A reads 0) *and* the **positive control** proving the fenced thing is real (B reads 42). The fence is **structurally blind, not merely weak** — neutering the emission a rollback test guards leaves the atomicity assertion GREEN (the zeroes are identical whether it rolled back or never ran) and only the control goes red, so the control carries 100% of the discriminating power. Corollary: `security-guide`'s SEC rows name **both** arms (*"→ rejected `SCOPE_VIOLATION`"* **and** *"by store owner → succeeds, audited"*); a task discharging only the denial arm has not discharged the row — a denial test with no positive control is indistinguishable from an endpoint that rejects everything, including the legitimate call. Incidents (review-47's own probe green for the wrong reason; task 17 F3's atomicity test blind to a neutered emission): [`incidents.md`](incidents.md) INC-T17. |
| **T-19** | **`??` and `\|\|` on a value you failed to READ is a lie generator — it converts "I don't know" into a plausible answer.** A default is correct when the *absence* is meaningful (an optional field the caller may omit); it is a defect when the absence means **the read failed**, because the fallback then manufactures a value indistinguishable from a real one and every downstream check reads it as fact. **The actual discriminator is not the operator but the plausibility of the fallback in the domain:** `?? null` is fine — `null` announces itself and the type forces a check; `?? 0`, `?? ''`, `?? 1` are not, because nobody double-takes a plausible number. **Rules:** (1) when `?? x` follows a read that can fail, ask what distinguishes *failed* from *legitimately x* — if nothing does, **throw or return `null`** (ask: if this default fired, would anything downstream look different?); (2) `NaN` is a **better** outcome than a plausible default because it propagates loudly while `0`/`1`/`""` propagate silently; (3) a hash, a sequence number, and a byte count are the three worst places for a default. **And the fix belongs at compile time when the runtime cannot see it** — when the production driver runs in no test lane, widening a return to `number | null` turns a silent launder into a `TS18047` compile error, the only place the guarantee can live. Incidents (`pull.ts:411`'s plausible serverSeq 1; `hashFile`'s empty-string SHA-256; `sizeOf`'s 0 bytes; `repository.ts`'s op-sqlite `?? 0`): [`incidents.md`](incidents.md) INC-T19. |
| **T-18** | **The task-notification is a §2.1 wrapper, and it reports on itself.** A background-task completion — *"completed (exit code 0)"* — describes **the wrapper process**, not the command you cared about; a subagent's final report is the same shape (prose from a process that may itself have read a reaped log). Rules: **(1)** a notification or agent report is a **prompt to go read the log**, never the result; **(2)** before believing a suite result, check it has a **denominator** — `Test Files N passed`/`Tests N passed` — because *no output* renders identically to *nothing failed*; **(3)** `wc -c` the log when a run finishes suspiciously fast; **(4)** never gate a merge/commit/delete/"done" on either (CLAUDE.md §2.1). The Bash tool caps at **600 s** while the suite and `test:rls` run near it, so **the flake and the fake green are the same event** — run long suites detached, then read the log for its denominator and `EXIT=`. **(5)** `/tmp` is shared across every agent worktree, so a log path is not a provenance — write scratch under the worktree or `$CLAUDE_JOB_DIR/tmp`, never bare `/tmp/<generic>.log`; if a peer may have touched your tree mid-run, **discard the run**. Corollary: `pkill -f "<tool>"` **matches its own command line** and reaps peers — never pattern-kill by tool name in a shared session. Incidents (the 145-byte "exit 0" reaped vitest; the EXIT=143 minutes later; impl-61's 43-minute-stale `/tmp/final.log`): [`incidents.md`](incidents.md) INC-T18. |
| **T-14** | **A coverage check must assert its own denominator.** Any sweep, enumeration, or parse-driven assertion SHALL name and check the total it expects to cover: an aggregate item count (floor set below today's real number so growth never trips it, but a starved parse fails loudly), non-zero units per parsed group, or the exact set where the set is fixed. A loop over an empty or truncated collection passes silently — the failure mode of a guard must never be "verified nothing (or a fraction), reported green". Incidents (a codegen sweep checking 19 of 164 properties; a `relkind='r'` RLS sweep omitting views; an SEC-id gate matching a mention): [`incidents.md`](incidents.md) INC-T14. |

Money in any fixture or assertion is **integer IDR** — a float literal in a payload fixture must fail the same lint that guards production code (`05 §3`).

## 2. Test pyramid and environments

### 2.1 The layers

| Layer | What it proves | DB | Crypto | Where it runs | Runner |
| ----- | -------------- | -- | ------ | ------------- | ------ |
| **L1 unit** | Pure core logic: JCS canonicalization, hashing, chain construction, canonical-order comparator, command handlers with stub `ctx` | none | `@noble/curves` 2.2.0 + `@noble/hashes` 2.2.0 | Node CI, every PR | vitest |
| **L2 client integration** | Command runtime + projection engine end-to-end (append → project → query) against real SQLite | better-sqlite3 `:memory:` behind the `kysely-generic-sqlite` 2.0.0 shim (§2.3) | `@noble` | Node CI, every PR | vitest |
| **L3 server integration** | Push/pull validation pipeline, RLS tenancy, migrations | **Real PostgreSQL 16 in a container (testcontainers `@testcontainers/postgresql` 12.0.4, image `postgres:16`) over the real `pg` driver** — one container per suite run, migrated ONCE into a template database, each test file cloning its own DB via `CREATE DATABASE … TEMPLATE` (§2.5). **This is the only L3 DB engine for driver/RLS/version-sensitive claims (D16).** PGlite remains ONLY as an explicitly-scoped dialect pre-filter (§2.4, T-14f rule 3) and is never a sole witness | `@noble` | Node CI, every PR | vitest |

| **L7 Hermes vectors** | RFC 8785 + hash/signature vectors execute correctly on Hermes (JCS number serialization depends on spec-correct ES number→string; Hermes must be proven, not assumed) | none | `canonicalize` 3.0.0 + `@noble` | CI: Metro-bundled vector runner executed by the Hermes VM binary; re-run redundantly inside L6 | hermes CLI |

vitest is the Node-side runner; its exact version is pinned in the lockfile at implementation time (it was not covered by the stack-research pass — do not treat any vitest version cited elsewhere as spec).

### 2.2 Crypto interop suite (runs in L1 and L6)

`@noble` (server/CI) and `react-native-quick-crypto` (device) must be RFC 8032-interoperable. A shared golden vector file (`@bolusi/test-support/vectors/ed25519.json`) contains: known 32-byte seeds → expected public keys, known messages → expected signatures (Ed25519 is deterministic, so signatures are byte-comparable). L1 asserts `@noble` reproduces every vector; L6 asserts quick-crypto reproduces every vector AND cross-verifies (`@noble`-produced signatures verify under quick-crypto and vice versa via the vector file). The same file carries SHA-256 vectors and the RFC 8785 test vectors (Appendix of the RFC) used by L7. Adding a vector requires a change to `05-operation-log.md` or this doc first.

### 2.3 Client DB engine decision (normative)

op-sqlite is a JSI native module and **cannot run in Node** — CI needs a different driver, but the Kysely dialect layer must be identical or CI proves nothing about the device.

- There is exactly **one** client dialect implementation: a custom shim built on `kysely-generic-sqlite` 2.0.0 (no official op-sqlite Kysely dialect exists), with **two driver adapters** behind one driver interface: `better-sqlite3` (in-memory) for Node/CI, `@op-engineering/op-sqlite` 17.1.2 for device. better-sqlite3's exact version is pinned in the lockfile at implementation time (not version-verified by research).
- A **driver conformance suite** in `@bolusi/test-support` runs the identical statement set (types round-trip, transaction commit/rollback, prepared-statement reuse, batch insert, error mapping) against both adapters — better-sqlite3 in CI, op-sqlite in L6 — and asserts identical results. This is what licenses "green in CI ⇒ meaningful on device".
- The op-sqlite single-connection rule (one open connection per database, app-wide) is mirrored in the harness: each virtual device owns exactly one connection to its own DB.
- SQLCipher is OFF in CI (better-sqlite3 has none; encryption-at-rest is not what L2–L5 prove) and ON in L6.

### 2.4 Applier conformance suite (T-8 mechanism)

For every module: take a fixed seeded op script (§3.3), fold it through the projection engine once against the SQLite shim and once against PGlite, dump both via the oracle (§3.4), assert byte-equal digests. This is the "shared test suite that runs every applier against both engines" required by `04 §2`. It runs in L2+L3 on every PR touching the module.

**Read T-8's scope clause before trusting a green here.** This suite answers exactly one question — *do the appliers depend on SQL dialect?* — and its op-log fixture DDL deliberately mirrors the **client** schema (`payload text`, `agent_initiated integer`, per db-client's `001-initial-schema.ts`), not the server's (`payload jsonb`, `agent_initiated boolean`). So it is not, and is not trying to be, a statement about the server op log or about what the production driver hands back. Two things follow, and both have bitten:

- **Marshalling is out of scope by construction.** Both legs return `int8` as a number; real `pg` returns a string (T-14f). No amount of work inside this suite fixes that, because the gap is the *client*, not the dialect. Marshalling claims belong on `pnpm test:rls` — which under D16 is real PG16 in a container over real `pg`. **This scope limit survives D16 deliberately** (T-8, and it is a ruling): the leg cannot move, because `core` may import neither `pg` nor `db-server` (the latter is a dependency cycle), and it does not need to — rule 3 permits a substitute precisely when something else is the witness, and now something is.
- **The pull path is not exercised at all.** The suite calls `applyAppendedOp` for every op, so `engine.ts`'s `source === 'append'` branch is the only one that ever runs. `highestContiguousServerSeq` — and therefore `applied_server_seq` — is untouched here on either engine.

### 2.5 Server tenancy tests (RLS)

**Under D16 this suite runs on real PostgreSQL 16 in a container, over the real `pg` driver — not PGlite.** The owner-bypass trap below is the reason it was never safe on a substitute, and it does **not** go away by switching engines: **testcontainers' default `postgres` user is a SUPERUSER, and superusers bypass RLS even under `FORCE ROW LEVEL SECURITY`.** Swapping PGlite for a container while still connecting as the default user would swap one vacuous RLS lane for another and call it progress (D16 says this in as many words). What makes the lane non-vacuous is the ROLE, not the engine. Therefore, normative:

1. Migrations create a dedicated non-superuser, non-owner role (`bolusi_app`, `NOBYPASSRLS`) and production connects as it; RLS tests execute `SET LOCAL ROLE bolusi_app` inside the test transaction before any tenant-table access. Tables are owned by `bolusi_provision` and carry `FORCE ROW LEVEL SECURITY`, so even the owner is subject to the predicate — the superuser is the only bypass left, and the role switch is what closes it.
2. A catalog assertion runs in CI: every table carrying a `tenant_id` column has `pg_class.relrowsecurity = true` and at least one policy — a new tenant table without RLS fails the build.
3. Adversarial cases (mandatory): query without `set_config('app.tenant_id', …, true)` returns zero rows / fails closed; a `forTenant(A)` handle can never read tenant B rows even when the WHERE clause is deliberately omitted at the repository layer (proving RLS is the backstop, not the filter); `set_config` with `is_local = true` does not leak across two sequential transactions on the same pooled connection.
4. **SUPERSEDED BY D16.** This used to read *"PGlite is the fast loop, real Postgres is the drift check"* — a deliberate, reasonable tradeoff that the repo then measured and disproved. The substitute did not merely lag the real thing; it was **blind to exactly the bug class that fails silently** (int8 marshalling: PGlite 14/14 GREEN vs real `pg` 4 RED, tasks 46/48/73), while catching the classes that throw. A "drift check" that only runs after the fast loop is green cannot help when the fast loop is green *because* it cannot see the defect. **So there is no fast/drift split any more: L3's DB is real PG16 over real `pg`, always.** The speed argument that motivated the split is also void — see note 5: the substitute was the *cause* of the slowness, not the cure for it.
5. **The lane's shape (task 73), and why each part is load-bearing.** ONE `postgres:16` container per suite run → migrate ONCE into a template database → **each test file clones its own database via `CREATE DATABASE … TEMPLATE`** (a filesystem copy, milliseconds; no WASM boot, no re-migrate). Each file owning a real database is what removes the reason `fileParallelism: false` existed *on this lane* — the shared database every file reset — so it is re-enabled.
   **DO NOT REPEAT THE SPEED CLAIM THIS ROW ORIGINALLY MADE.** It said PGlite's per-file WASM boot was *why* `fileParallelism: false` was set, and that the real lane is therefore faster. **False, and corrected by review-73 with a one-line experiment nobody had run.** Measured, same 15 files: compose real-PG serial **216.72 s** → this lane **45.35 s** (4.8× vs the lane it replaces, real); PGlite serial ~46 s; **PGlite with `--fileParallelism`: 14.40 s** — i.e. **this lane is ~3× SLOWER than parallelised PGlite**. PGlite was never serialized for cost: main's own config says it was serialized to "buy identical behaviour across both lanes", matching the shared-DB postgres lane. **The lane exists for FIDELITY, not speed** — the substitute is blind to the silent class (measured four times: PGlite 14/14 GREEN vs real PG16 4 RED on the same int8 defect). Two wrong causes have now been asserted for this one phenomenon (first "the box is oversubscribed" on a 96%-idle box, then "WASM boot"); both were plausible, neither was measured. If you catch yourself explaining a performance number, run the experiment instead.
   Three rules keep it honest:
   - **Never connect to the template after migrating it.** `CREATE DATABASE … TEMPLATE` fails while ANY session holds the template (`DETAIL: There is 1 other session using the database.`). Not for a health check, not for codegen. The clone helper asserts zero `pg_stat_activity` rows for the template and **fails with that reason** rather than retrying.
   - **The cap is `max_connections` (default 100, minus `superuser_reserved_connections` = 3), not database count.** Databases are cheap; connections are the resource. Size `maxParallelFiles × poolPerFile + headroom` under it, and shard to a second container rather than raising `max_connections` unboundedly (each backend is a process with its own `work_mem`).
   - **No `.withReuse()`.** It reads like free speed and it is not: `withReuse()` returns *before* testcontainers registers the container with Ryuk and never applies the `session-id` label Ryuk reaps by, so a reused container is **never cleaned up** and outlives the run that made it. That is the leaked-container class of T-14d, re-created by the mitigation (a 13-day-old orphan with exactly that label fingerprint was found on this box). Ryuk — which reaps on `SIGKILL`, however the runner dies — is the main structural reason to prefer testcontainers over the hand-rolled compose lane, and reuse trades it away for the ~2 s of one container boot amortised across the whole suite.

## 3. Part B — The chaos harness (normative spec)

The harness is monorepo package `@bolusi/harness` (workspace layout and import boundaries per `08-stack-and-repo.md` §3). It depends only on public packages (`@bolusi/core`, `@bolusi/server`, the `notes` module manifest) plus `@bolusi/test-support` fakes (also a workspace package per `08` §3). ### 3.1 Fixture architecture

```
Harness(seed, config) = {
  server:  { app: Hono fetch handler (production @bolusi/server),
             db: PGlite, clock: FakeClock (server), seeded tenant/store/users/devices },
  devices: VirtualDevice × N (default N = 4),
}

VirtualDevice = {
  identity:  deviceId, storeId, userId set, Ed25519 keypair

  db:        own SQLite via the shim (§2.3) — better-sqlite3 :memory: in CI, op-sqlite file on device,
  runtime:   production command runtime + projection engine + sync engine,
  clock:     own FakeClock — independently settable/skewable per device,
  net:       FaultFetch(server.app.fetch) — fault-injecting fetch wrapper (§3.5),

```

Devices are pre-enrolled in the server fixture (pubkeys registered, device tokens issued) unless a scenario says otherwise. Each virtual device holds its own chain state (`seq`, `previousHash`) purely as a consequence of running the production append path.

### 3.2 Reference module requirements

The `notes` module (`04 §8`) is the harness workload. Two testability requirements on its projection (additive to the `04 §8` checklist):

1. The `notes` projection table shall include `edit_count` (integer, incremented by each `notes.note_body_edited` apply) — declared as a testability column in `01-domain-model` §9 and in both notes DDLs in `10-db-schema`. A last-write-wins-only projection cannot reveal double-application; `edit_count` makes any idempotency violation visible to the oracle.
2. The schema-migration seam (v1→v2→v3 payload fold, incremental apply AND full rebuild) is covered by `packages/modules/test/migration.test.ts`, which builds real signed ops per version. The op script generator does NOT carry a `schemaVersion`/cutover seam: a scripted op maps to a real `notes` command and the runtime stamps `schemaVersion` from the operation registry (`ctx.ts` `resolveSchemaVersion`, never caller-supplied), so a generator-side version descriptor was dropped at the command boundary and was deleted (task 132).

### 3.3 Determinism kit (`@bolusi/test-support`)

| --------- | ---- |

| FakeClock | `{ now(): number, advance(ms), set(ms) }` — injected into runtimes per T-6. One per device + one for the server. |

### 3.4 The convergence oracle (defined once; every convergence assertion uses it)

`digest(db, module)` — engine-neutral, byte-exact:

1. Tables = the module's projection tables per its manifest, ascending byte order of table name. **Excluded:** the op log, watermark tables (`applied_server_seq`/`applied_local_seq`), all client bookkeeping (`syncStatus`, `syncedAt`, …), `SyncState`, `quarantined_ops`.
2. For each table, `SELECT` the manifest-declared columns in declaration order — all rows, **no SQL ORDER BY** (collation differs across engines; sorting happens in JS).
3. Normalize each scalar:

   | Stored value | Normalized |
   | ------------ | ---------- |
   | NULL | `null` |
   | integer (incl. pg `int8` returned as string) | JSON integer; if magnitude > 2^53 − 1 → decimal string |
   | boolean-declared column (pg `true/false`, SQLite `0/1`) | `1` / `0` |
   | text | JSON string |
   | blob / `bytea` | `"0x"` + lowercase hex |
   | any float / non-integer numeric | **oracle ERROR** — floats are banned from projections (`05 §3`); the oracle enforces it |

4. Each row → `JCS([tableName, v1, …, vn])` (RFC 8785 via the same shared implementation ops use, `05 §3`).
5. Sort all row-lines of the whole module ascending by UTF-8 byte order; `digest = SHA-256( join(lines, "\n") + "\n" )`.

**Convergence** = digests byte-equal. The **canonical-fold reference** for an op set: fresh DB via the shim, insert nothing, feed all ops to the production projection engine strictly in canonical order `(timestamp ASC, deviceId ASC, seq ASC)` (`05 §4`), then `digest()`. Every convergence scenario asserts: each device's digest == every other device's == the server's == the canonical-fold reference.

### 3.5 Fault-injection points (used by CHAOS-02/09)

`FaultFetch` injects, per scheduled (requestIndex, point):

| Point | Meaning |
| ----- | ------- |
| **F1** | Request never reaches the server (network error before send). |
| **F2** | Server processes the request fully; response lost. |
| **F3** | Response received; client process "crashes" before persisting the outcome (per-op statuses / cursor). Simulated by discarding in-memory state and re-opening the device DB. |
| **F4** | Pull only: local apply-transaction commits; crash before cursor persists (`api/01 §4` — cursor is written after the atomic apply). |
| **F5** | Pull only: crash mid apply-transaction (transaction rolls back). |

"Every batch boundary" means: for a backlog forming **B** push batches and **C** pull batches, the scenario runs once per (boundary k ∈ [0, B+C], applicable fault point) pair.

### 3.6 Scenario catalog

Every scenario: takes a seed; asserts with unique per-seed values (T-3); prints the seed on failure. PASS criteria are exhaustive — anything beyond them observed as a diff (extra ops on server, extra rows in dumps) is a failure.

**CHAOS-01 — Out-of-order arrival (projection convergence, FR-1118 / 04 §4.2)**
- *Setup:* 3 devices, script of 500 ops each incl. same-entity contention; all offline (no sync during generation).
- *Action:* Deliver every device's ops to every other device and the server in PRNG-shuffled arrival order (via sync where possible; direct engine feed for arrival-order permutations the protocol itself cannot produce). Must hit both `04 §4.2` paths: ops that arrive canonically-newest for their entity (head case) and ops that sort before an already-applied op (re-fold case) — the harness asserts both counters > 0 via the engine's public stats, or fails as inconclusive.
- *PASS:* All device digests == server digest == canonical-fold reference.

**CHAOS-02 — Interrupted sync at every batch boundary (FR-1122)**
- *Setup:* 1 device with 1,600 local ops (4 push batches of ≤ 500 per `api/01 §3`); server holding 1,600 foreign ops (4 pull batches).
- *Action:* For every (boundary, fault point F1–F5) pair per §3.5: run the sync loop, inject, then let the loop resume (fake-timer backoff per `api/01 §6`).
- *PASS:* After resume completes: server op count == exactly 1,600 pushed ops (no loss, no dupes — F2 retries must come back `duplicate`, never re-insert); every pushed op `syncStatus = synced`; device digest == canonical-fold of all 3,200 ops; pull cursor == final `serverSeq`; no batch was skipped (F4 re-pull was an idempotent no-op, F5 re-pull re-applied).
- *SCALE (heavy scenario — §3.7 policy):* runs at the FULL 1,600 + 1,600 volume in the merge gate over a **bounded seed sweep** (the first CI seed only; nightly and any explicit `CHAOS_SEEDS=` run every seed), and a representative boundary per fault (the full boundary × fault cartesian is the nightly's). The volume is never cut — the seed sweep is the documented knob (one full-volume case ≈ 50 s; a 10-seed sweep serializes to ~55 min).

**CHAOS-03 — Days-offline bulk merge (FR-1123)**
- *Setup:* 4 devices offline 7 simulated days, ~500 ops/day each via FakeClock advancement (≈ 3,500 ops/device).
- *Action:* Reconnect devices one at a time, full sync each.
- *PASS:* Convergence (all digests == canonical fold of all ~14,000 ops); pull was incremental — each device's pull transferred only ops it lacked (assert transferred-op counts, no re-download of the world); push batching respected ≤ 500 ops per batch.
- *SCALE (heavy scenario — §3.7 D-CHAOS-SCALE; the worked example for the VOLUME lever):* the single-seed full 14,000-op case is **MEASURED at ~591 s** on a quiet box (90 % inherent server round-trips + Ed25519 verify — 14,000 push-verifies + ~42,000 pull re-verifies across the 4-device merge; the fold itself is < 1 s), so bounding the seed sweep alone still leaves a ~10-min gate file. Uniquely for CHAOS-03 the CI gate therefore ALSO reduces the VOLUME — **CI: ~5,040 ops** (4 devices × 7 days × ~180 ops/day, ~1,260/device ⇒ **3 push batches/device**, chosen to cross the batch-split + cursor-pagination + incremental-pull thresholds); **nightly: the FULL 14,000** (and ×4 under the nightly rule). The reduction is **DOCUMENTED and self-guarding, never silent**: the CI test asserts `pushBatches ≥ 2` and non-zero incremental foreign-pull per device, so a future drop below the split threshold reds the gate (positive control — §2.11 / T-14). Both volumes preserve the 7-day days-offline **structure** (only ops/day is reduced — FR-1123 is a days-offline merge). The seed sweep is bounded to the first CI seed either way; nightly / explicit `CHAOS_SEEDS=`/`CHAOS_SCALE=` run the full volume — and the nightly ×4 lane (56,000 ops/seed ≈ 40 min) runs that volume over a capped seed sample (**CHAOS-03 → 3 seeds**, §3.7 lever 3).

**CHAOS-04 — Clock skew (05 §6)**
- *Setup:* Device A clock +72 h, device B clock −72 h, both `lastSyncAt` < 1 h ago (so threshold ≈ 48 h); device C offline 5 simulated days with +72 h skew (threshold ≈ 48 h + 120 h — within allowance); device D honest.
- *Action:* All generate ops, all sync.
- *PASS:* A's and B's ops: accepted with `clockSkewFlagged = true` — **never rejected** (`05 §6`: assume drift, not malice); C's ops: accepted, `clockSkewFlagged = false`; D unflagged. Flagged ops appear in projections like any other. Convergence holds — canonical order uses `timestamp` as written, so ordering stays deterministic even with A's ops sorting "in the future".

**CHAOS-05 — Tampered chain / rejection matrix (05 §8, api/01 §3)**
- *Setup:* Enrolled device with a valid 20-op chain, pushed. Tamper cases are built with the raw wire client (§3 preamble).
- *Action / PASS (exact codes, exact `results[].status`):*

  | Case | Mutation | Expected |
  | ---- | -------- | -------- |
  | T1 | Payload field modified; `hash`/`signature` untouched | `rejected` / `BAD_SIGNATURE` (server recomputes the JCS hash; signature fails against it) |
  | T2 | Payload modified and re-signed with a non-enrolled key | `rejected` / `BAD_SIGNATURE` |
  | T3 | `previousHash` set to a wrong value | `rejected` / `CHAIN_BROKEN`; every later op in the same batch `rejected` / `CHAIN_HALTED` (`api/01 §3`); client halts push and surfaces |
  | T4 | Two ops' `seq` values swapped (reorder) | first out-of-order op `rejected` / `CHAIN_BROKEN` |
  | T5 | `seq` skips ahead (gap) | `CHAIN_GAP`; client re-pushes from the gap; all ops eventually `accepted` — not an error state |
  | T6 | `tenantId` of another tenant, correctly signed | `rejected` / `SCOPE_VIOLATION` (`05 §9`, fail closed) |
  | T7 | Push from a revoked device (Device.status `revoked` — terminal, `03-state-machines`) | HTTP 401 + ops `rejected` / `DEVICE_REVOKED` (`api/01 §2`) |

**CHAOS-06 — Duplicate replay / backup-restore (05 §5)**
- *Setup:* Device A with 300 synced ops; server converged.
- *Action:* (a) Re-push A's last 2 batches verbatim (simulated lost-ack retry). (b) Clone A's DB file to device A′ (same keys, same chain — a backup restore), reset A′'s in-memory state, run its sync loop. (c) Feed a pull batch containing 50 ops A already holds.
- *PASS:* (a)+(b): every replayed op returns `duplicate`; server op count and each op's original `serverSeq` unchanged. (c): pull-applying an op whose `id` exists locally is a no-op. All digests unchanged — in particular every `edit_count` value (§3.2) identical before/after, proving no projection double-application.

**CHAOS-07 — Concurrent same-entity edits, 2+ devices (04 §8; conflict classification per 01 §8)**
- *Setup:* Devices A, B, C share one synced note. All go offline; each edits the same note's body with a distinct seed-derived value. Sub-case (i): distinct timestamps. Sub-case (ii): **identical `timestamp`** on A and B (tie forced via FakeClock) — so the tie resolves on `deviceId`. Sub-case (ii-seq): an **intra-device same-millisecond** tie — two edits from **one** device sharing `timestamp` AND `deviceId`, distinct `seq` — so `deviceId` also ties and the tie falls through to the final canonical-order component, `seq`. Sub-case (iii): a second synced note — device A archives it while device B, offline, edits its body (edit-after-archive).
- *Action:* Sync all in PRNG-chosen order. In sub-case (iii), after the conflict surfaces, an owner device acknowledges it (appending `platform.conflict_acknowledged`) and syncs.
- *PASS:* Convergence everywhere. Winning body = the canonically **last** op's payload under `(timestamp ASC, deviceId ASC, seq ASC)` — asserted against the explicitly computed winner; in the tie sub-case the op from the greater `deviceId` (byte order) wins; in the intra-device same-millisecond sub-case (ii-seq) `deviceId` also ties, so the op with the greater `seq` wins — deterministically, on every device and the server. `edit_count` = total edits from all devices (no edit lost even when overwritten). Conflict classification per `01 §8`: sub-cases (i) and (ii) each produce a Conflict record `{key: 'note.body', severity: 'minor'}` that walks `detected → auto_resolved` (LWW outcome stands; the record stays queryable, never surfaced); sub-case (iii) trips the Rule-2 invariant check `notes:edit_after_archive` at server fold → Conflict `severity: 'significant'`, `detected → surfaced`, then `surfaced → acknowledged` on every device once the acknowledgment op syncs. Both Conflict resting transitions (`auto_resolved`; `surfaced → acknowledged`) are thereby exercised (D4).

**CHAOS-08 — Projection rebuild mid-stream (04 §4.3, FR-1116)**
- *Setup:* Device with 20,000-op history; a control device holding the identical op set that never rebuilds.
- *Action:* (a) Start full rebuild; kill the process (state discard + DB reopen) at 25/50/75% of the watermark; resume — rebuild must continue from the watermark, not restart. (b) Start full rebuild while 500 new ops arrive interleaved via pull and local commands.
- *PASS:* Post-rebuild digest == control device's incremental digest == canonical fold including the mid-stream ops. Rebuild resumability proven by watermark monotonicity (never re-applies below the watermark after resume).
- *SCALE (heavy scenario — §3.7 policy):* runs at the FULL 20,000 + 500 volume in the merge gate over a **bounded seed sweep** (the first CI seed only; nightly and any explicit `CHAOS_SEEDS=` run every seed). At 20,000 ops a case is ~54 s and a file's tests run serially, so the old seeds-1–10 sweep serialized this one file to ~9 min and was the gate's long pole. The nightly additionally lifts the volume to ×4 (80,000), sampled over a capped seed set (**CHAOS-08 → 5 seeds**, §3.7 lever 3) — the ×4 volume is never run at all 100, and the cap is asserted, not silent. The volume is never cut; the seed sweep is the documented knob.

**CHAOS-09 — Media upload interruption at every chunk boundary (api/03-media)**
- *Setup:* MediaItem of `4 × chunkSize + 3` bytes (uneven final chunk; `chunkSize` per `api/03-media`), PRNG-filled content, client-side SHA-256 recorded at capture.
- *Action:* For every chunk boundary k and fault points F1–F3: interrupt, then let the foreground drain loop resume. Plus one mid-chunk truncation case (partial chunk body).
- *PASS:* Upload completes; server-assembled bytes' SHA-256 == the client's recorded SHA-256; server never stores a chunk twice (received-chunk tracking); truncated chunk is rejected and re-sent cleanly; `uploadStatus` walks only `pending → uploading → (failed → uploading)* → uploaded` (`03-state-machines`; `uploaded` terminal); the op referencing the media synced independently of media completion (`api/01 §8`).

**CHAOS-10 — gzip bomb + malformed gzip on push (stack: bearerAuth → bodyLimit → decompression cap → zValidator)**
- *Setup:* Server with production middleware chain; caps at their production values.
- *Action / PASS:*
  | Case | Input | Expected |
  | ---- | ----- | -------- |
  | G1 | Wire bytes ≤ `bodyLimit`, decompressed size > decompressed cap (gzip bomb) | rejected `413`; decompression aborts at the cap (bounded memory — assert the stream was not fully expanded) |
  | G2 | Truncated gzip stream | rejected `400` |
  | G3 | `Content-Encoding: gzip` with non-gzip bytes | rejected `400` |
  | G4 | Wire bytes > `bodyLimit` | rejected `413` before decompression runs |
  | G5 | Valid gzip within both caps | `200`, ops processed normally |
- *PASS (all):* zero ops persisted from G1–G4; the immediately following valid push (G5 re-run) succeeds — the server survives.

**CHAOS-11 — PIN rate-limit escalation timing (FR-1011; lockout machine owned by api/02-auth §6.5)**
- *Setup:* Enrolled user with a known PIN; auth module with FakeClock; the escalation schedule (attempts 1–3 free; consecutive-failure delays 30 s / 60 s / 120 s / 300 s cap; hard lockout at the 10th failure) imported as the auth package's exported constants — this scenario must not duplicate the numbers as literals.
- *Action:* Repeated wrong-PIN attempts, advancing FakeClock precisely around each configured delay; then the two recovery paths.
- *PASS:* Delays match the schedule exactly under FakeClock: an attempt at `delay − 1 ms` throws `PIN_RATE_LIMITED`, at `delay` is accepted for evaluation. During a delay window or lockout, attempts (wrong **or correct** PIN) are refused **without executing argon2id** (KDF-invocation spy count unchanged — no battery/timing oracle): `PIN_RATE_LIMITED` while `delayed`, `PIN_LOCKED` while `locked_out`. The 10th consecutive failure enters `locked_out` and emits `auth.pin_locked_out`; a successful PIN before that resets the counter to 0. Recovery is **offline-only** (`api/02-auth` §6.5 — there is no online self-recovery path to assert): owner unlock via `auth.clearPinLockout` (permission `auth.pin_unlock`) and owner PIN reset via `auth.resetPin` each clear the lockout under FakeClock with zero network calls (FaultFetch asserts none). Lockout state survives a simulated restart (state discard + DB reopen) via `pin_attempt_state`, and a FakeClock rollback never shortens a `notBefore` window. Attempt/lockout observability per `api/02-auth` §6.5: per-attempt records in local state, `auth.pin_locked_out`/`auth.pin_lockout_cleared` ops as the tenant-synced evidence (FR-1045 analog for auth events).

**CHAOS-12 — Pull-side injection (api/01 §4.2: trust, but verify)**
- *Setup:* Harness server variant that injects into a pull response one op with a bad signature and one op signed by a key not in the device's `device_registry`.
- *Action:* Device runs its pull loop. Later, the harness server adds the unknown key to the devices sidecar (bumping `devicesDirectoryVersion`) and the device pulls again.
- *PASS:* Per `api/01 §4.2`: the bad-signature op is quarantined immediately; the unknown-pubkey op triggers exactly **one** re-pull with `devicesDirectoryVersion: 0` (fresh sidecar) and — still unknown — is then quarantined. Quarantine is asserted on the client `quarantined_ops` table: both ops present there, absent from projections and the applied set; the pull cursor **advances past both** (one bad op never bricks sync); the failure is surfaced loudly (label key `sync.quarantine.*`, asserted per T-4). Subsequent valid pulls still work. When the later sidecar update delivers the missing pubkey, the quarantined unknown-key op is re-verified, applied via the engine's out-of-order path, and leaves `quarantined_ops`; the bad-signature op stays quarantined. Unverifiable history never enters projections silently, and untampered devices still converge.

### 3.7 CI wiring and v0 exit mapping (D4.1)

| Decision D4 clause | Scenario(s) |
| ------------------ | ----------- |
| multi-device sync simulation | fixture §3.1 (all scenarios) |
| out-of-order arrival | CHAOS-01 |
| clock skew | CHAOS-04 |
| interrupted/resumed sync | CHAOS-02, CHAOS-09 |
| tampered chains rejected | CHAOS-05, CHAOS-12 |
| days-offline merge | CHAOS-03 |
| idempotent replay | CHAOS-06 |
| projection rebuild against realistic history volume | CHAOS-08 (Node) + P-2 (device, §4) |

Every PR: seeds 1–10, CI-scale volumes (as written above). Nightly: 100 random seeds, volumes ×4, plus the real-Postgres L3 job — with ONE stated exception: the two heavy scenarios run the ×4 volume over a capped seed sample (**CHAOS-03 → 3 seeds**, **CHAOS-08 → 5 seeds**; §3.7 lever 3), every other scenario keeps all 100. v0 exit additionally requires the L6 on-device run green (§2.6) — CHAOS-01/03/06/07 at reduced volume plus all of Part C, on the physical reference device.

**Heavy-scenario scale policy (D-CHAOS-SCALE — TWO levers, both explicit, never a silent trim).** Several scenarios (**CHAOS-02** interrupted-sync, **CHAOS-03** days-offline merge, **CHAOS-08** projection rebuild) are heavy enough that the standard "seeds 1–10 at CI volume" would dominate the merge gate. **vitest parallelizes at the FILE level**: the tests *within* one scenario file run **serially**, so a single heavy file at 10 seeds serializes to many minutes and becomes the gate's long pole, while files run concurrently with one another. Two levers keep the gate honest; which one(s) a scenario uses is decided by its **measured single-seed cost**:

- **Lever 1 — bound the CI SEED sweep (the default for every heavy scenario).** Run the FULL §3.6 volume in the gate over the **first CI seed only**; the nightly (and any explicit `CHAOS_SEEDS=…` reproduction) runs every seed. Each scenario gates its seed list behind a small helper (`chaos02Seeds`/`chaos03Seeds`/`chaos08Seeds`: `CHAOS_SEEDS` or `CHAOS_NIGHTLY=1` ⇒ all resolved seeds, else `.slice(0, 1)`) with an in-file comment flagging the bound. **The nightly must NOT be bounded too** (a bounded-both silently drops coverage) — the helpers return the full `resolveSeeds(env)` under `CHAOS_NIGHTLY=1`/explicit seeds, verified by test-collection count (1 in CI, 100 nightly). CHAOS-02 (~50 s/case, 3,200 ops) and CHAOS-08 (~54 s/case, 20,000 ops) use ONLY this lever — one seed at full volume fits the gate.

- **Lever 2 — reduce the CI VOLUME to a DOCUMENTED, threshold-crossing level (only when a single full-volume seed exceeds the gate budget).** When even one full-volume seed is too expensive, the gate additionally runs a **reduced** volume, with the FULL volume run in the nightly. This is NOT a silent cut (§3.6 forbids that, and §2.1 forbids a run that quietly tests less): the reduced volume is (a) chosen to **cross the real thresholds** the scenario exists to exercise, (b) **stated in the header + this doc**, and (c) **enforced by a positive control** — the CI test asserts it still crosses those thresholds, so a future drop below them reds the gate. **CHAOS-03 is the worked example** and the reason lever 2 exists: its single full-volume seed is **MEASURED at ~591 s** (14,000 ops, 4-device merge; ~90 % inherent server round-trips + Ed25519 verification — 14,000 push-verifies + ~42,000 pull re-verifies — with the fold itself < 1 s; the cost is volume-proportional and unremovable without cutting volume, since production crypto/PGlite are T-7). Bounding seeds alone still left a ~10-min gate file. So CHAOS-03's CI gate runs **~5,040 ops** (4 × 7 days × ~180 ops/day, ~1,260/device ⇒ **3 push batches/device**) — crossing the batch-split, cursor-pagination, and incremental-pull thresholds — and asserts `pushBatches ≥ 2` + non-zero incremental foreign-pull per device (drop below 500/device and that assertion reds, watched). The **days-offline structure is preserved** (7 FakeClock days at reduced ops/day, not fewer days — FR-1123 is a days-offline merge). The **nightly runs the full 14,000** (and ×4 under the nightly rule).

What lever 1 bounds is the seed dimension only; what lever 2 reduces is stated and self-guarded. Neither ever silently reduces the properties asserted (CHAOS-02 still runs every fault point at a representative boundary; CHAOS-03 still asserts all three PASS properties at whatever volume it runs; CHAOS-08 still does the 25/50/75 % kill-and-resume watermark proof). Because the reproduction command carries the scale (`CHAOS_SEEDS=N CHAOS_SCALE=S`), a nightly failure reproduces verbatim; CHAOS-03's genuinely-long full case carries an explicit per-test timeout (30 min × `CHAOS_SCALE` full / 10 min CI-reduced) — a legitimately heavy computation with load headroom, never a masked hang.

- **Lever 3 — cap the NIGHTLY ×4 SEED SAMPLE, per scenario (the nightly job's lever, not a scenario's).** The nightly runs 100 seeds at ×4. For the two heavy scenarios that lane is not merely slow, it is **unrunnable**, and an unrunnable job is a coverage *claim* with no coverage behind it (§2.11): **CHAOS-03** at ×4 is 56,000 ops/seed ≈ **40 min/seed** (volume-proportional from the measured 591 s / 14,000 ops) ⇒ ~2.7 **days** for 100; **CHAOS-08** at ×4 is 80,000 ops/seed ≈ 3.6 min ⇒ ~6 h for 100, the whole nightly budget in one file. So the ×4 lane runs those two at the **full ×4 VOLUME over a capped SEED SAMPLE** — the volume is never cut (4× volume is the entire point of the lane); only the seed dimension is:

  | Scenario | Nightly ×4 seed sample | Every other scenario |
  | -------- | ---------------------- | -------------------- |
  | CHAOS-03 → 3 seeds | ~2 h at ×4 (56,000 ops/seed) | the full **100 seeds at ×4** |
  | CHAOS-08 → 5 seeds | ~18 min at ×4 (80,000 ops/seed) | (uncapped — this is a two-row exception, not a trim) |

  The cap is a **job-level** knob, deliberately NOT part of a scenario's own seed policy: it lives in one registry (`packages/harness/src/nightly-scale.ts` → `NIGHTLY_X4_SEED_CAPS`), applies **only** on the ×4 nightly lane (`CHAOS_NIGHTLY=1` **and** scale > 1 **and** no explicit `CHAOS_SEEDS=`), announces itself per scenario in the nightly log, and is restated in `.github/workflows/chaos-nightly.yml`. `chaos03Seeds`/`chaos08Seeds` still return **every** resolved seed for an explicit reproduction (guardrail #2 above) — the printed `CHAOS_SEEDS=… CHAOS_SCALE=…` command runs exactly what it says. `CHAOS_X4_SEED_CAP=<n>` deepens a particular nightly. **Asserted, never silent** (`scenarios/nightly-seed-cap.test.ts`): the heavy scenarios' ×4 lane resolves to the capped sample *out of a denominator that is verified to be the full 100*, the light scenarios resolve to 100, the two scenario files are verified to actually **call** the cap and no other file does (T-16), a config resolving zero seeds throws rather than collecting an empty sweep (T-14), the three statements of the number are compared to each other, and the CI lane is asserted to be an exact pass-through. Because a chaos case's cost is volume-proportional, the **timeout ceilings scale with `CHAOS_SCALE`** too — the harness vitest config's default (120 s at CI ⇒ 480 s at ×4, off the same `activeVolumes` seam) and CHAOS-03's explicit per-test ceiling (30 min × scale). A flat ceiling below the ×4 case's own runtime (CHAOS-08 at ×4 is ~216 s against a 120 s default; CHAOS-03 at ×4 is ~40 min against a 30 min one) would red the whole lane as a budget artefact, not a bug. The CI gate never runs ×4.

### 4.1 The seed: `SEED-200K` (year-equivalent history)

**200,000 operations**, generated deterministically (seed 42) via the §3.3 generator scaled to ~20,000 entities × ~10 ops each, plus 5,000 MediaItem metadata rows. (The generator carries no schema-version cutover — see §3.2.2; the v1→v2→v3 fold is covered by `packages/modules/test/migration.test.ts`.)

*Justification:* one busy store's daily op volume, estimated from the v1 module PRDs — POS ~60 sales × 2 ops = 120; repairs ~12 × 8 lifecycle ops = 96; inventory movements ~40; finance ~30; attendance ~40; misc ~50 ⇒ ≈ 380–560 ops/day. At ~550/day × 360 days ≈ 198k. A device pulls its own store + tenant-scoped ops (`api/01 §4.1`), so 200k is a defensible upper bound for one device-year; at ~600 bytes/op it is ≈ 120 MB of log — realistic for the 32GB device. Gates hold at 200k or the gate fails — no "it was close".
