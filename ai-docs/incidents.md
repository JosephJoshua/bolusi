# Incident Log — why the testing disciplines read the way they do

> **What this file is.** The **normative rules** live where they are enforced and read on the hot path: CLAUDE.md §2.11 (the one-paragraph discipline), `testing-guide.md` T-11…T-19 (one imperative line each), and `sec-pending-allowlist.json`'s machine-read `id → owning-task` map. This file holds the **incident record** those rules were distilled from — the war stories, the measured numbers, the falsifications — so the hot-path docs stay short and the *why* stays recoverable.
>
> **A rule is not weakened by living here.** Nothing in this file is optional; nothing here is the source of a rule. If a T-row's one-liner and an incident here ever disagree, the T-row wins (it is the contract; this is the evidence).
>
> **Citation contract.** Every `INC-*` anchor cited from CLAUDE.md, `testing-guide.md`, or `sec-pending-allowlist.json` MUST resolve to a heading in this file. `packages/test-support/src/incidents-citations.test.ts` enforces it: a dangling `INC-*` pointer fails the build. Add a section here before you cite it.

## INC-T11 — gates that were green for the wrong reason

The discipline "**a guard is only load-bearing if someone has watched it go red**" (CLAUDE.md §2.11, testing-guide T-11) exists because v0 shipped, at last count, **eight** gates that passed while checking nothing — plus a ninth that could not run at all:

1. **SEC-META-01** matched file *content*, not test titles — a SEC id mentioned anywhere in a file read as "shipped".
2. **codegen-diff** was made permanently unsatisfiable by prettier reformatting its own input — the diff could never be empty, so it was routed around.
3. The **boundary rule**'s platform-free prong *exempted the Hermes-bound files it existed to protect*.
4. **`badOwners`** matched a *mention* of a SEC id, so a task **disclaiming** an id ("that's task 07's") satisfied it.
5. A **codegen sweep** looped over a regex parse that, if the generated format changed, would check **zero** properties and report green.
6. The **i18n key-grammar gate** read *catalogs* while the parking mechanism (`SEED_DEFERRED_KEYS`) kept parked keys **out** of catalogs — so it was green **because** the illegal keys were invisible to it, and the same blindness exempted every module-owned row (real denominator **113 of 127**).
7. A **`test:rls` green** was served by *another worktree's database* after an unread `db:up` failure (see INC-T14D).
8. The **`codegen-diff` gate was inoperable for a second, unrelated reason**: task 34's `${DATABASE_URL:?…}` guard message contains **three apostrophes** (odd count), and `${VAR:?msg}` messages are **shell-parsed**, so `dash` died with `Syntax error: Unterminated quoted string` and `pnpm db:codegen:check` could not run at all. It reported *"no drift"* because **the diff was empty because codegen never ran**.

Each was found only by running the mechanism. Two lessons the last one carries:

- It was introduced **by the fix for another fake green** — task 34 existed to eliminate unattributable greens and created one, in the very message that cites INC-T14D. **A fix is not exempt from the rule it enforces.**
- **An inoperable gate and a passing gate are the same colour.** The only way to know a gate runs is to make it go red on demand; it was caught because an agent saw `EXIT=0, no drift` and asked *why* the diff was empty instead of banking it.

Two of these deserve special notice: the **parking** case (6) and the **CI-placeholder** case are guards that were green *because of* the very mechanism meant to defer or stand in for the work — so "deferred" and "done" became indistinguishable to the checker. **When you add a skip/park/placeholder path, ask immediately: does the checker still see what I just set aside?**

## INC-T12 — test the class, not the instance

`AA=A` (padding position) and `zh==` (non-canonical padding **bits**) are the same base64 validator's problem but **different classes** — a fix for one collapses none of the other's 16 variants. A test suite built from remembered examples can only catch remembered examples. When a bug is found, ask what *class* it belongs to and enumerate that class programmatically.

## INC-T13 — interrogate the oracle

Node's `Buffer.from(s,'base64')` accepts `AA=A`, `A A=`, `AA%3D`, `≡A==`, and `=` — so a base64 validator tested *against Node's decoder* **cannot fail**: the oracle is looser than the code under test. Before trusting a comparison, ask what decides "correct" in it, and whether that thing is stricter than the code under test. A hand-typed golden vector has already been wrong here (`25` vs `5c`) — extract vectors programmatically from their source spec, never by hand.

## INC-T14 — a coverage check with no denominator

Three sweeps in one session were *green about the wrong question* because none checked the size of what it looked at: a codegen sweep that checked **19 of 164** properties under partial parse degradation; a `relkind='r'` RLS sweep that omitted views entirely; an SEC-id gate that matched a mention. Each was caught only by making the guard state its expected total and watching it go red when starved. A loop over an empty or truncated collection passes silently — the failure mode of a guard must never be "verified nothing (or a fraction), reported green".

## INC-T14B — an empty result and a correct result look identical

This environment's docker daemon is shared. A parallel process reset the schema mid-probe (DROP SCHEMA + re-migrate leaves tables and policies but **zero rows**), and the RLS probes returned `UPDATE 0` / `0 rows` — *which reads as flawless tenant isolation and was completely vacuous*. Caught only by an inline fixture assertion that the row it expected to be filtered out actually existed first. A local `pnpm test:rls` green here means nothing without that assertion (CI is unaffected — isolated service container). This is INC-T17's positive-control problem in the data plane.

## INC-T14C — a stale build is a fake green

`@bolusi/core`'s jcs-guards tests import `dist/index.js`; the Hermes vector runner imports `src/crypto/jcs.js`. A `pnpm test` with no preceding `tsc -b` produced a green mutant run that detected nothing — it tested yesterday's build — and nearly fooled a reviewer who rebuilt before believing the numbers. Two lanes importing different artifacts (`dist/` vs `src/`) can silently test different code. Guard it: make `test` depend on `build`, make both lanes import the same entry, or assert build-freshness (dist mtime ≥ src mtime). CI that runs `tsc -b` before the test stage is protected; a bare local `pnpm test` is not.

## INC-T14D — know which database answered

The dev `docker-compose.yml` published a **fixed** host port (`127.0.0.1:5432:5432`) and `test:rls` targeted a **hardcoded** `localhost:5432`, so on this shared daemon only the FIRST worktree to `db:up` bound the port. Every later worktree's `db:up` failed (`Bind for 127.0.0.1:5432 failed: port is already allocated`, EXIT=1) and its DB tests then **silently connected to another worktree's database**, applied their migrations there, and went green. Task 13's gate verification reported "82/11 on real PG16" — from **task 05's leaked container**, because `db:up` ran as `>/dev/null 2>&1` and its EXIT=1 was never read. The result happened to be real (right engine, right migrations) — which is exactly what made it dangerous: the number was correct and the reasoning behind it was fiction. Two worktrees running DB tests concurrently share one database and corrupt each other's fixtures — surfacing as flakiness (T-10), not misconfiguration. CI was unaffected (isolated service containers), so **local and CI disagreed about whether isolation exists**, and only local lied.

**Closed by task 34, by construction rather than discipline** — the "never redirect `db:up`" rule this incident first produced was itself a *discipline* fix for a defect §2.1 had already failed to prevent once. It was replaced by mechanism: the host port is now **ephemeral and per-worktree** (never re-pin `ports:` to 5432); `DATABASE_URL` is derived from `docker compose port` by `scripts/db-lane.mjs`, which makes a failed `db:up` **fatal to the lane** so no DB test can follow one; every dev cluster is **stamped at init** with the compose project that owns it (`bolusi.db_owner`), which `packages/db-server/test/global-setup.ts` verifies before any test runs, aborting on a foreign *or absent* stamp. What survives as a rule: **believe a DB number only if its run printed the `attribution OK` provenance line**, and never `docker compose down` a container that is not yours (`pnpm db:down` only ever removes your own).

## INC-T14E — a number is scoped to the worktree that measured it

Task 32 recorded "stage 8 = 22 files / 162 tests" in `08-stack-and-repo.md` §7 as evidence. Task 13's identity suites merged first, and main was **33 files / 199 tests** by the time the record landed — true when measured, stale when quoted, quoted in a *spec*. The author cannot catch this: they measured correctly, in a tree that by definition predates the merge. Only a reader at merge time can. This failure mode scales with parallelism — the more agents in flight, the more likely main has moved under any branch's evidence. Same class as the leaked-container green (INC-T14D): a number whose provenance does not match where it is cited — but far more benign, because it was honest at the instant of measurement. Rules preserved in the T-row: re-measure durable-doc numbers against the merged result; if you cannot re-measure, cite the scope ("22/162 *as of merge-base `abc123`*"); reviewers check quoted numbers against main, not the branch.

## INC-T14F — "both engines" is not "both drivers"

T-8's applier-conformance gate proves SQL *dialect* neutrality by running better-sqlite3 and **PGlite**. Neither is the production client. **The real `pg` driver returns `int8`/`bigint` as a STRING** (int8 exceeds JS's safe integer range, so node-postgres refuses to coerce lossily); better-sqlite3 and PGlite both return a **number**. So any code doing arithmetic or `===` on a bigint column is correct in every test lane and broken in production.

- **The incident (task 46):** `highestContiguousServerSeq` compared `row.serverSeq === watermark + 1` — `"1" === 1` is `false`, so the server projection watermark **never advanced on real Postgres**, silently, with no error and no red test. Verified on PG 16.14: `bigint -> "1" typeof=string`; `int4 -> 1 typeof=number`.
- **The obvious test for it is the bug's alibi (verified in Node, task 17):** the defect is **lexicographic ordering over differing DIGIT COUNTS**, not magnitude. `"10" > "9"` → **false** (bites); `"100" > "99"` → **false** (bites); but `"9007199254740993" > "9007199254740992"` → **true** — *correct by luck*, because equal-length strings compare digit by digit. So the instinctive probe — a value near **2^53** — goes **GREEN with the bug fully present** and licenses the conclusion that the cast is not load-bearing. impl-17 reached for exactly that instance first and caught itself. The mental model "this is about bigints" selects the alibi; the accurate model is "this is about string ordering", and 2^53 is where the *marshalling* starts, not where the *comparison* breaks.
- **The type argument lies about KEY NAMES too:** `CamelCasePlugin` (wired into production at `db-client/src/connection.ts:185`) rewrites **raw `sql` result keys**, so `sql<{byte_size: number}>` over a bare `SELECT byte_size` arrives as `byteSize` — every read is `undefined`, and `Number(undefined)` is **`NaN` on the wire** (task 18). `NaN` is worse than a throw: silent, typechecks, lints, reaches the server. Write explicit aliases (`byte_size AS "byteSize"`). The family has three members — task 39 (`DB` resolved to `any`, so `tsc` checked nothing across `apps/server`), task 46 (`sql<{serverSeq: number}>` over int8), and task 18 — and the shared mechanism is that **a hand-written type argument is a claim `tsc` accepts without evidence**.
- **The D16/task 73 answer for L3 is fixed and a gate may simply cite it:** `postgres:16` in a testcontainer, over real `pg` 8.22.0, connecting as `bolusi_app` (NOBYPASSRLS). Any gate still running a substitute states the substitute **by name** and names the lane that carries the claim it cannot make.
- **`.withReuse()` is a provenance defect of the same family:** it makes the container survive the run that created it, so the next run's "real PG16" may be a *previous* run's container with a *previous* run's schema — INC-T14D wearing testcontainers. A reviewer *identified this exact mechanism* one task earlier and correctly sized the instance in front of it as a nit (that function had the cast); the **class** was never swept, and the neighbouring function did not. Finding the mechanism is not finding the class (T-12).

## INC-T14G — a test can go inert *because the fix landed*

Every other entry here is a guard that never worked. This one **worked, then stopped**. Task 46: a 2^53 boundary test seeded a row beyond a gap and asserted a throw. Under the **first** implementation (per-row narrowing) that row *was* read and *did* throw — the test genuinely found the flaw. The fix moved narrowing to a single exit point, so the row is never read; and because the test's `from` was `2^53` (itself **not** a safe integer — `MAX_SAFE = 2^53 − 1`), the walk now throws at its **first statement**, before any row. **Deleting the seeded row left 98/98 green.** Two different errors existed and the oracle `/server_seq/` matched both, so the mislabel was invisible (INC-T13 — the oracle was looser than the claim). The property was still true; the test had stopped being the thing proving it. Rules preserved in the T-row: re-derive what a test executes after a shape-changing fix; a fixture that can be deleted with no effect is inert (prove load-bearing setup by deleting it and watching red); make the oracle as narrow as the claim (`/exceeds/` distinguishes the two throws, `/server_seq/` cannot).

## INC-T14H — a loud failure is the only witness the silent ones have

Task 48: `RawOpRow` carried three bugs — jsonb (`JSON.parse` **throws**), int8 (`"10" < "9"` — canonical order inverts past seq 9, **silent**), and boolean (`false !== 0` → every op reads agent-initiated, **silent**). Measured on real `pg` with all three present: **9 failed / 110 passed, 10 SyntaxError, 0 AssertionError — not one ordering or attribution oracle spoke.** In isolation the int8 bug produces 4 RED and the boolean bug 1 RED; together with jsonb they contribute **exactly zero signal**. So "fix the obviously-broken thrower first" would have shipped two silent corruptions **with nothing watching them**. The trap is invisible to counting: 9 red before, 5 red after fixing jsonb, which every reviewer reads as *progress*. Rules preserved in the T-row: when a path throws, assume it is **masking** — revert-in-isolation to measure each bug's own signal; **count failure modes, not failures** (`10 SyntaxError, 0 AssertionError` is the tell your oracles never ran); a partial fix on a multi-bug path is worse than none.

## INC-T15 — when the answer to "what would notice?" is *nothing*

Found in one sweep (review-05), same question, three shapes — all green, none visible to a test, type, lint, or exit code:

- **(a) a well-typed no-op** — `keystore.ts:34` sets `keychainAccessible: WHEN_UNLOCKED_THIS_DEVICE_ONLY`, an **iOS-only** option, as the sole cited enforcement of §7.4 on an **Android-first** product (task 58). The constant is exported for every platform, the option is honoured by one; the field is silently dropped at runtime. `tsc` cannot catch this class at all — it checks correctly and the check is *irrelevant*.
- **(b) a write the OS ignores** — `applyChannelImportance` passes `importance:` to `setNotificationChannelAsync` on an existing channel, which Android forbids post-creation (task 59). The Promise **resolves**. No throw, no error, no exit code: it **succeeds at doing nothing**.
- **(c) a test on a decoy** — `canAttempt` has 11 sound assertions and **zero callers**; break `pinPadState`, the line that actually gates the pad, and all 11 stay green (task 60). Coverage measures whether a line ran **under test**, never whether it runs **in production**.

**The common cause: the comment was the guard.** Each site had an accurate, specific, spec-citing comment, and each is why nobody checked — `notifications.ts` states Android's immutability rule at line 4 and **violates it at line 61, twelve lines down, one author, one sitting, past review**. A comment that authoritative doesn't merely fail to prevent the bug below it; it **supplies the reader's confidence** so they stop checking. Prose is in no gate's denominator.

**And the guard can be the other platform (audit 80).** `expo-location` is **not registered** in `app.config.ts`'s plugins, and `Root.tsx` requests location on **every boot**. On Android this works — the permissions reach the manifest by **library-manifest merging**, i.e. by accident of the build system. On iOS `infoPlist` is `null`, and Apple documents termination for a location request with no usage description. So **Android's correctness was the thing hiding iOS's defect**. The same shape waits for `expo-camera` (task 82). Related, in upstream code: `@expo/prebuild-config/getPrebuildConfig.js:60` does `bundleIdentifier ?? config.ios.bundleIdentifier ?? 'com.placeholder.appid'` — the same line serves both platforms, Android sets `package` so it never reaches the fallback, and iOS silently ships a placeholder identity. **Generalisation: when a claim holds on platform A and is unverified on platform B, A's success is not evidence — it is the mechanism concealing B's failure.**

**The rule works when applied — one caught prospectively (task 18):** `getFreeDiskStorageAsync` — the familiar, still-widely-documented API — **throws at runtime** on SDK 54+; the implementer checked the platform column in current SDK docs *before* writing and used `Paths.availableDiskSpace` instead (`apps/mobile/src/media/files.ts:9-10,39`). Found before shipping, by treating the docs as the oracle rather than their own recall.

**A correction that is itself an instance of INC-T16:** an earlier revision of the T-15 row credited task 18 with catching `BackgroundTask.registerTaskAsync`'s silent return on `Restricted`. **That catch has no producer — zero `BackgroundTask` code exists in the task.** The SDK behaviour is real (doc-confirmed) and the implementer noted it; but noting a hazard is not catching it. The orchestrator wrote it **from an agent's report, without tracing to a producer — inside the rule that says to trace to a producer**, and review-18 caught it.

## INC-T16 — a mention is not a producer, and it lies in both directions

`grep` answers *"is this string here?"* — never *"does this behaviour exist?"* — and the two are uncorrelated **both ways**, which makes mention-counting worse than useless: it produces a confident number pointing the wrong way. Measured, twice in one hour, by the same author, **after** he wrote the warning into task 52:

- **(a) a mention made dead code look alive.** A grep sweep for exported-but-uncalled functions reported **109 findings across 462 exports and missed `canAttempt`** — the one case it was written to find — because the only non-test mention of `canAttempt` is *the false comment that is the defect*.
- **(b) an ABSENCE of a mention made live behaviour look dead.** Task 31's SEC audit read test *titles*, saw `SEC-AUTH-06/11` titled only *"client arm"*, and concluded the server legs were unshipped. Task 54 was filed on that. **The legs ship** — in task 07, under titles carrying no id at all (`scope.ts:107-118`, four arms incl. both positive controls, `4 passed EXIT=0`). The premise was refuted by the implementer.

**The ring is the recurring shape — three instances, each a whole feature that never existed.** The failure is a **cycle of mentions where every file names another and nobody builds it**, and each pointer reads as diligence:

- **task 49** — the server never applied projections: `08` → *"lands with 07/16"*, **`07` mentions "projection" ZERO times**, `16` → *"task 17's"*, `17` did one table, `25` assumed a registry nobody created.
- **task 50** — the **SQLCipher key that encrypts the entire on-device database** had **two consumers and zero producers**: `db-client/src/connection.ts` declared and consumed `getDatabaseEncryptionKey`, its comment claimed *tasks 14/24 supplied it*, `keystore.ts` **disclaimed** it, and `KeyStorePort` **never declared it**. impl-50 settled it by construction: `TS2741: Property 'getDatabaseEncryptionKey' is missing`.
- **task 43** — auth appliers, same shape.

The tell is that the ring is only visible from outside it: each file is locally coherent and cites a real task number. **The instrument that breaks a ring is the compiler or the language service, not reading** — careful reading is what built it.

**Discipline-proof, so do not rely on discipline.** The author broke this rule **three times in one session** — the decoy sweep, task 54's dead premise, and task 58's, whose grep of `apps/` answered *"is the exclusion in the shipped manifest?"* with *"is this string in my source?"* while the same file's Acceptance section warned that `app.config.ts` is not the artifact. So the operative form is not "remember to trace" but **answer existence questions by PRODUCING the thing**: resolve the prebuild config, ask the language service, run the migration, read the generated manifest. **If your evidence is a text search, you have not answered the question you asked.**

**An instrument's false-negative is worth more attention than its false-positive — and you will only ever notice the latter.** impl-18's first FR-1138 test was a mention-counter (substring-matching `operations` in comments). It **went red**, so the author looked and fixed it. Had the file contained no prose about `operations`, it would have gone **green and been believed**. Its own words: *"a mention-counter that cries wolf gets fixed; one that stays quiet gets believed."* This is why *"my sweep found nothing"* is the least trustworthy sentence in this repo — **before believing a green sweep, make it go red on a known case.**

**The same trap catches PERFORMANCE explanations — two authors on one task.** The orchestrator asserted *"PGlite's per-file WASM boot forced `fileParallelism: false`"*; impl-73's own `vitest.config.ts` comment asserted the identical false mechanism — while the config file one directory away held the refutation in plain English: *"serialising costs a little time and buys identical behaviour across both lanes."* Neither ran the one-line experiment: `--fileParallelism` → **46 s becomes 13.94 s**, same 130 tests, `EXIT=0`. PGlite was serialised for **consistency**, never cost. **If you catch yourself EXPLAINING a performance number, run the experiment instead** — a causal story about timing sounds like analysis, is a guess, and no type/test/lint will ever contradict it.

## INC-T17 — a fence test needs a positive control

An isolation assertion — *"tenant A cannot read tenant B's row"*, *"the revoked device's ops are not accepted"*, *"no plaintext token is in the DB"* — is satisfied **trivially** if the thing it fences never existed. `expect(rowsVisibleToA).toBe(0)` passes when B's write silently failed, when the seed didn't land, when the fixture targeted the wrong table. The green means "absent", and "absent" is exactly what a broken setup also produces.

**review-47's own first cross-tenant probe was green for the wrong reason**, inside a review *of* this failure class — it asserted A reads 0 without first proving B's write landed. It survived only because the reviewer asked *"what would notice?"* (INC-T15) about its own probe. The corrected version proved both halves on real PG16: B's write lands (B reads 42), an A-bound handle constructing the store with B's `tenantId` reads **0, not 42**, and the cross-tenant write is **rejected**.

**The fence is structurally blind, not merely weak (task 17, F3).** Its atomicity test asserted a failed mid-batch emission leaves `ops` unchanged and `system_device_chain_state.last_seq === 0`. Neutering **the emission itself** — so nothing was ever emitted to roll back — left the **ATOMIC test GREEN** and turned only the **positive control** red. The zeroes are identical whether they mean *"it rolled back"* or *"it never ran"*; the fence cannot tell those apart even in principle, and the control carries 100% of the discriminating power. (The task's *original* test failed this way for a subtler reason: it aborted from `systemIdentity`, which resolves **before** the emission loop — so `appendSystemOp` never ran and the assertion was trivially true. Caught by review-17, not the suite.) This is why `security-guide`'s SEC rows name **both** arms (*"→ rejected `SCOPE_VIOLATION`"* **and** *"by store owner → succeeds, audited"*), and why a task discharging only the denial arm has not discharged the row.

## INC-T18 — the task-notification is a §2.1 wrapper, and it reports on itself

A background-task completion — *"completed (exit code 0)"* — describes **the wrapper process**, not the command you cared about. Measured (review-47): a full-suite run was reported **"completed (exit code 0)"** while its log held **145 bytes and zero test results** — vitest had been **reaped** when the wrapper returned. Nothing failed, nothing warned; the notification was, in its own terms, accurate.

**Fired again within minutes of the rule being written, on the orchestrator, in the opposite direction.** A backgrounded `pnpm test; pnpm lint; pnpm typecheck` chain notified **"completed (exit code 0)"**; a re-run of the same `pnpm test` returned **`EXIT=143`** (SIGTERM) writing **182 bytes with no denominator**. *(The orchestrator first wrote "the two runs collided" here — a cause asserted with no evidence, in a rule about not asserting things with no evidence. A peer later reported its own `pkill -f "vitest"` had matched the word inside its own command line, killing its wrapper and plausibly every concurrent run. The true cause is still not established: SIGTERM records that something killed it, not who. "EXIT=143" is evidence; "because X" was a story.)* Note which artifact caught it: not the notification, not the exit code — the **byte count and the missing `Test Files N passed` line**.

The Bash tool caps at **600 s** while this repo's suite and `test:rls` (~400 s) run near it, so a passing suite and a reaped one are separated by load — **the flake and the fake green are the same event**. Run long suites detached, then read the log for its denominator and `EXIT=`.

**`/tmp` is shared across every agent worktree, so a log path is not a provenance (impl-61):** its "final" verification run read `/tmp/final.log` — **another agent's file, timestamped 43 minutes earlier**. A real number, a fictional provenance, byte-identical to a real one — INC-T14D wearing a filesystem. Write scratch under the **worktree** or job dir (`$CLAUDE_JOB_DIR/tmp`), never bare `/tmp/<generic-name>.log`; if a peer may have touched your tree mid-run, **discard the run**. Corollary: `pkill -f "<tool>"` **matches its own command line** and reaps peers — never pattern-kill by tool name in a shared session.

## INC-T19 — a default on a value you failed to READ

A default is correct when the *absence* is meaningful (an optional field the caller may omit). It is a defect when the absence means **the read failed** — the fallback then manufactures a value indistinguishable from a real one. Three instances, all one session, none caught by a type or a lint:

- `sync/pull.ts:411` — `Number(rows[0]?.maxSeq ?? 0) + 1` over a raw `sql<T>` whose key resolves only via `CamelCasePlugin`: a missing key returns a **plausible `serverSeq` of 1**, and "no rows" vs "key not found" become the same fact (task 74).
- `apps/mobile/src/media/files.ts` — a dead `?? 0` in `hashFile` meant hashing a **missing file** returned the **empty-string SHA-256**: a real-looking 64-hex digest the `HASH_MISMATCH` path reads as *"your evidence rotted"* (task 18).
- the same file's `sizeOf` returned **0 bytes** for a missing file instead of rejecting, violating its own port contract.

**The actual discriminator (impl-18):** the operator is not the problem; **the plausibility of the fallback in the domain** is. `?? null` is fine — `null` announces itself and the type system forces a check. `?? 0`, `?? ''`, `?? 1` are not, because nobody double-takes a plausible number. Ask: *if this default fired, would anything downstream look different?* If not, throw or return `null`. **And the fix belongs at compile time when the runtime cannot see it:** `repository.ts`'s `Number(result.numAffectedRows ?? 0)` runs under the production driver (**op-sqlite**) which is in **no test lane** (no device), so a silent driver would launder to `0` only in production. Changing the return to `number | null` made `if (recovered > 0) requestDrain()` a **`TS18047` compile error** — the guarantee lives at compile time because that is the only place it can live.

## INC-SEC-AUTH-09 — the discharge (2026-07-25, task 28)

SEC-AUTH-09 was **DISCHARGED** 2026-07-25 (removed from `sec-pending-allowlist.json`; titled verbatim by `packages/harness/test/security/sec-auth-09.test.ts`). All three legs are proven:

- **LEG 2** (no pushed op payload carries verifier material) — `packages/harness/test/security/sec-auth-09-payloads.test.ts`, titled for invariant I-13, with its planted-byte positive control (INC-T14B / T-17).
