## Why this is filed (the D24 option-C premise, falsified at the producer — 2026-09-03)

D24 (`ai-docs/decisions/2026-09-02-owner-ruling-181-device-server-chaos.md`) ruled that CHAOS-03/06/07 run on-device against the REAL host `@bolusi/server` because **"the device already reaches it — the P-3 perf gate already hits that host server over lab Wi-Fi"** (D24 lines 13, 17–18). Traced to producers, that premise is **false at four independent points** — the exact T-16 "a mention is not a producer" class CLAUDE.md §2 names. Superseded by `ai-docs/decisions/2026-09-03-defer-device-host-network-chaos-to-198.md`.

1. **The "harness server" is an in-process function, not a socket.** `packages/harness/src/server.ts:187` — `HarnessServer.fetch` is `(input, init) => Promise.resolve(app.request(input, init))`; the file header (line 3) states it is *"reached ONLY via `app.request` (no sockets)."* It is a Hono `app.request` handler over PGlite (WASM Postgres) in the SAME Node process as the test. Nothing on a device can `fetch` it.
2. **No TCP listener wraps it.** No producer stands `HarnessServer` up on a port — `grep -rE "@hono/node-server|serve\(|listen\(|createServer" packages/harness/src apps/mobile/src` returns nothing. The "host server" D24 pictures has no host process.
3. **No device→host route exists.** No `10.0.2.2` / `adb reverse` / host-IP mapping anywhere (`grep -rE "10\.0\.2\.2|adb reverse" packages apps scripts` → nothing). Even with a listener, a device could not address it.
4. **Synthetic devices are minted in-process, not over HTTP.** `HarnessServer.seedDevice` (`server.ts:196`) does a direct `INSERT INTO devices (… signing_key_public …)` on its PGlite `db` and returns `bdt_harness_${counter}` — an out-of-band token handoff inside the Node process. There is no HTTP self-enrollment a real device could use to obtain a device token (enrollment needs an operator `controlSession`; only `seedDevice` mints tokens).

And the gate D24 cited as proof the path works has **never run**: testing-guide §4.2 **P-3** (line 322 — the exact line D24 cites) sits under the D21 status block *"No gate in this table has been run … no p95, no ops/s … exists for any row"* (2026-07-22). So P-3 is ASSUMED-PASS, and its "§2.6 harness server" is the in-process `app.request` one of #1. Read to its source, D24's own citation refutes the claim.

**Net:** the device→host Wi-Fi sync path is **spec design intent** (testing-guide §2.6 line ~99: "on-device chaos scenarios point at a harness server (laptop, same Wi-Fi) via config") **with no producer**. Building that producer — and only then the three runners on top — is this task.
